# Observability

> **Status:** Normative. This defines structured logging, metrics, tracing, health checks, SLOs, alerts, and incident runbooks for operating Conductor in production.

## 1. Structured Log Schema

All Conductor components emit structured JSON logs to stderr.

### 1.1 Required Fields

Every log entry MUST include:

```json
{
  "timestamp": "2026-02-20T10:00:00.123Z",
  "level": "info",
  "message": "Phase transitioned",
  "service": "orchestrator",
  "component": "transition-engine",
  "run_id": "run_abc123",
  "project_id": "proj_xyz",
  "correlation_id": "corr_001",
  "trace_id": "trace_abc",
  "span_id": "span_xyz"
}
```

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `timestamp` | ISO 8601 | Yes | Millisecond precision |
| `level` | enum | Yes | `debug`, `info`, `warn`, `error`, `fatal` |
| `message` | string | Yes | Human-readable event description |
| `service` | enum | Yes | `control-plane`, `orchestrator`, `worker`, `watchdog` |
| `component` | string | Yes | Sub-component within service |
| `run_id` | string | When available | Run context |
| `project_id` | string | When available | Project context |
| `correlation_id` | string | When available | Cross-event correlation |
| `trace_id` | string | When available | Distributed trace ID |
| `span_id` | string | When available | Current span ID |

### 1.2 Log Levels

| Level | When Used | Example |
| --- | --- | --- |
| `debug` | Development-only detail | Agent prompt construction, SQL queries |
| `info` | Normal operations | Phase transitioned, run created, webhook received |
| `warn` | Recoverable issues | Rate limit retry, mirror deferred, stale run detected |
| `error` | Failures requiring attention | Agent timeout, DB error, auth failure |
| `fatal` | Process-level failures | DB connection lost, OOM, startup failure |

### 1.3 Sensitive Data

**Never log:** API keys, session tokens, OAuth tokens, GitHub App private keys, user passwords.

**Redact in logs:** GitHub access tokens (show first 4 chars), email addresses (hash), IP addresses (keep first 2 octets).

## 2. Correlation ID Propagation

Every request entering Conductor receives a `correlation_id` that propagates through all downstream operations.

### 2.1 ID Generation

| Entry Point | ID Source | Format |
| --- | --- | --- |
| API request | Generated by middleware | `req_<uuid>` |
| Webhook delivery | `X-GitHub-Delivery` header | GitHub-provided UUID |
| BullMQ job | Generated by producer | `job_<uuid>` |
| Agent invocation | Inherited from run | `run_<run_id>_inv_<seq>` |

### 2.2 Propagation Chain

```
HTTP Request (req_abc)
  → API Route (correlation_id: req_abc)
    → BullMQ Job (correlation_id: req_abc)
      → Worker (correlation_id: req_abc)
        → Agent Invocation (correlation_id: req_abc)
          → Tool Call (correlation_id: req_abc)
            → GitHub API Call (correlation_id: req_abc)
```

All events, logs, and metrics within a chain share the same `correlation_id`.

### 2.3 Run-Level Correlation

Within a run, the `run_id` serves as the primary correlation key. All events for a run can be queried by `run_id` regardless of which service produced them.

## 4. Health Check Endpoints

### 4.1 Control Plane

| Endpoint | Type | What It Checks | Healthy Response |
| --- | --- | --- | --- |
| `GET /api/health` | Liveness | Process is running | `{ status: "ok", version, timestamp }` |
| `GET /api/health/redis` | Readiness | Redis connection | `{ redis: "connected", latency_ms }` |
| `GET /api/health/db` | Readiness | SQLite accessible | `{ db: "ok", tables, migration_version }` |
| `GET /api/health/deep` | Deep | All dependencies | Combines all above + GitHub App status |

### 4.2 Worker

| Endpoint | Type | What It Checks |
| --- | --- | --- |
| Heartbeat (BullMQ) | Liveness | Worker process alive, sending heartbeats |
| Queue consumption | Readiness | Worker consuming from queues |
| Agent provider | Readiness | AI provider API reachable |

### 4.3 Health Check Thresholds

| Check | Healthy | Degraded | Unhealthy |
| --- | --- | --- | --- |
| Redis latency | < 10ms | 10-100ms | > 100ms or unreachable |
| DB query time | < 50ms | 50-500ms | > 500ms or unreachable |
| GitHub API | Rate limit > 100 | Rate limit 10-100 | Rate limit < 10 or unreachable |
| Queue depth | < 50 | 50-200 | > 200 |
| Worker heartbeat | Last < 60s | Last 60-120s | Last > 120s |

## 5. SLOs (Service Level Objectives)

### 5.1 Core User Journeys

| Journey | SLO | Measurement |
| --- | --- | --- |
| **Run creation** | 99.5% success rate | `conductor_runs_created_total / run_creation_attempts` |
| **Phase transition** | 99.9% succeed within 5s | `conductor_phase_transitions_total` (under 5s) |
| **SSE event delivery** | 99% within 1s of creation | `conductor_event_publish_lag_seconds` |
| **API response (reads)** | p95 < 200ms | `conductor_api_latency_seconds{method="GET"}` |
| **API response (mutations)** | p95 < 500ms | `conductor_api_latency_seconds{method!="GET"}` |
| **Webhook processing** | 99% within 10s | `conductor_webhook_processing_seconds` |
| **Run completion (happy path)** | 90% within 2 hours | `conductor_run_duration_seconds{result="completed"}` |

### 5.2 Error Budgets

| SLO | Budget (30-day) | Alert Threshold |
| --- | --- | --- |
| Run creation 99.5% | 0.5% failure allowed | Alert at 1% (2x budget) |
| Phase transition 99.9% | 0.1% slow allowed | Alert at 0.5% (5x budget) |
| API p95 < 200ms | 5% above threshold | Alert at 10% |

## 6. Alert Rules

### 6.1 Critical Alerts (Page)

| Alert | Condition | Severity | Response |
| --- | --- | --- | --- |
| `HealthCheckFailing` | `/api/health` returns non-200 for 2 min | Critical | Restart service, check logs |
| `RedisDown` | `/api/health/redis` returns error for 1 min | Critical | Check Redis, queues stalled |
| `DatabaseUnreachable` | DB query fails for 30s | Critical | Check disk, connections |
| `AllRunsBlocked` | 100% of active runs in `blocked` for 5 min | Critical | System-wide failure |
| `NoWorkerHeartbeat` | No heartbeat from any worker for 2 min | Critical | Restart workers |

### 6.2 Warning Alerts (Notify)

| Alert | Condition | Severity | Response |
| --- | --- | --- | --- |
| `HighErrorRate` | > 5% of API requests return 5xx for 5 min | Warning | Check logs, identify root cause |
| `QueueBacklog` | Queue depth > 100 for 10 min | Warning | Scale workers or investigate |
| `GitHubRateLimitLow` | Rate limit remaining < 100 | Warning | Reduce GitHub API calls |
| `RunStaleInPhase` | Run in same phase > 2x timeout | Warning | Check agent/watchdog |
| `DLQGrowing` | DLQ job count > 10 | Warning | Investigate, replay/purge |
| `SSEConnectionDrop` | > 50% SSE connections dropped in 1 min | Warning | Check network, Redis |
| `AgentErrorSpike` | > 3 agent errors in 5 min for same project | Warning | Check AI provider |

### 6.3 Informational Alerts

| Alert | Condition |
| --- | --- |
| `RunCompleted` | Run reached `completed` state |
| `NewProjectCreated` | Project created |
| `DailyDigest` | Daily summary of runs, errors, SLO status |

## 7. Incident Runbooks

### 7.1 Runbook: All Runs Stuck in Blocked

**Detection:** Alert `AllRunsBlocked` fires. Dashboard shows 0 active runs, N blocked.

**Triage:**
1. Check `/api/health` and `/api/health/redis` — identify which dependency is down
2. Check Redis: `redis-cli ping` — if PONG, Redis is fine
3. Check worker logs: `journalctl -u conductor-worker --since "5 min ago"`
4. Check GitHub App status: `GET /api/github/status`

**Mitigation:**
1. If Redis down → restart Redis, jobs will resume automatically
2. If AI provider down → wait for recovery, runs will retry
3. If auth error → check `GITHUB_APP_PRIVATE_KEY` env var
4. If DB error → check disk space, restart service

**Resolution:** Once root cause fixed, operator retries blocked runs via UI.

### 7.2 Runbook: Webhook Delivery Failures

**Detection:** Alert `DLQGrowing` fires for `webhooks` queue.

**Triage:**
1. Check DLQ: list failed webhook jobs with error messages
2. Common causes: webhook signature invalid (secret rotated), payload too large, normalization bug
3. Check GitHub webhook delivery history: Settings → Webhooks → Recent Deliveries

**Mitigation:**
1. If secret rotated → update `GITHUB_WEBHOOK_SECRET` env var, restart
2. If normalization bug → fix code, replay DLQ
3. If payload too large → check for oversized issue bodies

**Resolution:** Fix root cause, replay DLQ jobs, verify webhook deliveries resume.

### 7.3 Runbook: SSE Connections Dropping

**Detection:** Alert `SSEConnectionDrop` fires. Users report stale UI.

**Triage:**
1. Check Redis pub/sub: `redis-cli pubsub channels 'conductor:events:*'`
2. Check SSE connection count: `conductor_sse_connections` metric
3. Check reverse proxy timeout settings (nginx `proxy_read_timeout`)
4. Check for memory pressure on Next.js process

**Mitigation:**
1. If reverse proxy timeout → increase `proxy_read_timeout` to 3600s
2. If Redis pub/sub broken → restart Redis (SSE replay covers the gap)
3. If memory pressure → increase Node.js heap size or restart
4. Clients auto-reconnect with `Last-Event-ID` — replay limited to 100 events / 5 minutes (may return `refresh_required` if gap too large)

**Resolution:** Fix infrastructure issue, verify connections stabilize.
